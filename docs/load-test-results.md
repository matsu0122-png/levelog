# 障害試験・負荷試験

最終更新: 2026-09-23(フェーズ17)

このドキュメントは、フェーズ17「障害試験・負荷試験」で実施した「片系停止試験」「DBフェイルオーバー/リストア演習」「ロールバック演習」「負荷試験(ボトルネック調査を含む)」の結果をまとめる。

**実際のさくらのクラウードの有料リソース作成・`terraform apply`は本フェーズでも一切行っていない。** アプリサーバ・DBアプライアンス・ロードバランサいずれも実在しないため、本来の意味での実機試験(実際のさくらのクラウードLBのヘルスチェック挙動、実際のDBアプライアンスのフェイルオーバー、実際のGitHub Actions CDによるロールバック)はまだ実施できない。本フェーズでは、ローカルのDocker環境で本番構成に可能な限り近いシミュレーションを組み、実際のツール(`hey`によるHTTP負荷生成、実際のPostgres・Nginx・アプリケーションコード)で検証した。各試験の冒頭に、実機とどう違うか・何がシミュレーションで代替できないかを明記する。

## 1. 片系停止試験(ローカルシミュレーション)

**実機との違い**: さくらのクラウードのロードバランサ(`terraform/modules/load_balancer`)は、`/health/ready`への能動的(active)ヘルスチェックでバックエンドの生死を判定する。本試験では、オープンソース版Nginx(商用のnginx-plusや外部モジュールなしでは能動ヘルスチェック機能を持たない)の**受動的(passive)** ヘルスチェック(`max_fails`/`fail_timeout`、実際に転送を試みて失敗したときだけ切り離す方式)で代替した。検知の仕組みは異なるが、「1台が落ちても残り1台がトラフィックを処理し続けられるか」という試験したい性質そのものは同じ土台で確認できる。

### 構成

2つの独立した`api`コンテナ(同じ開発用DBを共有)+ Nginxの`upstream`ブロック(`proxy_next_upstream`で失敗したリクエストを即座にもう一方へ再試行)。

### 実施内容・結果

1. 両インスタンスが健全な状態で、`hey`により継続的な負荷(`GET /health/live`、同時接続5、20秒間)をLB経由でかけ続けた。
2. 負荷継続中に`docker kill`でapi1を強制停止(正常なシャットダウンではなく、実際の障害に近い形の突然の停止)。
3. 負荷生成を最後まで継続し、結果を集計。

**結果: 203,708リクエスト中、203,708件が200(失敗0件)。** レイテンシのほぼ全て(203,690件)が100ms未満だったが、api1停止の瞬間に居合わせたと見られる17件のみ約1秒(`proxy_connect_timeout 1s`の設定通り)かかった後api2へ再試行され、最終的に全て成功した。api1を停止した状態でもLB経由のリクエストは200を返し続けることを確認し、その後api1を再起動すると再びヘルシーな状態でLBの対象に復帰することも確認した。

**結論**: Nginxの`proxy_next_upstream`によるアウトバウンド再試行が機能する限り、1台のバックエンド停止はクライアントに一切のエラーを露出しない(接続確立に使う1秒だけごく一部のリクエストの尾部レイテンシが伸びる)。さくらのクラウードのLBは能動ヘルスチェックのぶん検知がより速いと考えられ、この結果はいわば「保守的な(受動検知という不利な条件での)下限」に相当する。実機でも同等以上の結果が期待できるが、実際のさくらのクラウードLBでの確認はアプリサーバ構築後に行う(フェーズ17の範囲では未実施)。

## 2. DBフェイルオーバー/リストア演習

**実機との違い**: さくらのクラウードのDBアプライアンスの実際のフェイルオーバー(レプリカへの昇格)は、`docs/database-design.md`3節の通りTerraformだけでは完結せず手動操作が必要であり、かつレプリカアプライアンス自体がまだ存在しないため試験できない。本節で実施したのは、**DBが完全に消える/戻るという障害そのものに対してアプリケーションがどう振る舞うか**の検証であり、フェイルオーバー(レプリカへの切り替え)そのものの検証ではない。バックアップからの復元(リストア)演習はフェーズ15で`pg_dump`/`pg_restore`により実施済み(`docs/backup-restore-design.md`)。

### 実施内容・結果

1. アプリケーションを起動し、`/health/ready`が200であることを確認。
2. DBコンテナを`docker stop`で停止。
   - `/health/ready`: **503**(想定通り。ロードバランサがあれば、これによってこのインスタンスはトラフィックの対象から外れる)
   - `/health/live`: **200のまま**(プロセス自体は生きている。これも想定通り — `/health/live`はDBに一切触れない設計、`docs/app-server-design.md`4節)
   - ログイン試行: **500**(JSON形式の一般的なエラーメッセージを返すのみで、内部情報の漏洩やパニック・クラッシュはなし)
   - アプリケーションプロセスのログにpanic/fatalが一切ないことを確認(プロセスは生存)。
3. DBコンテナを`docker start`で再起動。
   - **アプリケーションを再起動することなく**、`/health/ready`が自動的に200へ復帰することを確認。
   - 同じユーザーで新規登録が成功することを確認(DB接続プールが自動的に再接続していることの実証)。

**結論**: `pgx`のコネクションプールはDB切断からの自動再接続を正しく行い、アプリケーション側での特別なリトライ処理は不要であることを実機(ローカルDocker)で確認した。DB障害時も`/health/live`と`/health/ready`が正しく異なる状態を報告するため、ロードバランサの振り分けロジック(`/health/ready`ベース)が正しく機能する前提が満たされている。

## 3. ロールバック演習

**実機との違い**: `.github/workflows/cd.yml`の実際の実行(GHCRへのpush・SSHデプロイ)は行っていない(アプリサーバ・GitHub Secretsが未整備のため、`docs/deployment-design.md`6節からの既知の制約)。本演習では、`terraform/modules/app_server`の起動スクリプトが各サーバーに配置する`/opt/levelog/deploy.sh`の**ロジックそのもの**(`docker compose up -d`実行 → `/health/ready`を最大60秒ポーリング)を、実際にローカルで再現して実行した。`docker compose pull`の部分のみ、実際のGHCR認証情報がないため省略した(それ以外はスクリプトの内容と完全に同じ)。

### 実施内容・結果

1. 現在のコード(v1)をビルドし、`docker-compose.prod.yml`経由でローカルにデプロイ。`deploy.sh`と同じヘルスチェックポーリングが成功することを確認。ログイン等が正常に動作することを確認。
2. **意図的な退行を仕込んだコード(v2)**(ログインハンドラが常に500を返す、この演習専用の一時的な改変— 実リポジトリには一切コミットしていない)をビルドし、`IMAGE_TAG`を切り替えて同じ`deploy.sh`ロジックで再デプロイ。
   - **ヘルスチェック(`/health/ready`)は問題なく合格した**。`/health/ready`はDB疎通のみを確認する設計であり、アプリケーションロジックの個別の不具合までは検知できないため。これは設計上の意図した挙動(フェーズ2)だが、「ヘルスチェックが通った=デプロイが安全」ではないことを具体的に示す結果になった。
   - ログインが実際に500を返すことを確認(退行の「発覚」)。
3. `IMAGE_TAG`をv1へ戻して同じ`deploy.sh`ロジックで再デプロイ(ロールバック)。
   - ヘルスチェック合格、**ログインが再び正常に機能することを確認**。同じユーザー・同じDBに対して、コードだけを巻き戻して復旧できることを実証した。

**結論**: `IMAGE_TAG`を過去の値に戻して同じデプロイスクリプトを再実行する、という`docs/deployment-design.md`が想定するロールバック手順(1節)は、実際にその通りに機能する。同時に、ヘルスチェックだけでは検知できない種類の退行がありうることが分かったため、これを残課題として記録する(8節)。

## 4. 負荷試験

`hey`(`go install github.com/rakyll/hey@latest`)を使い、実際に起動したアプリケーション(ローカル開発用Postgres、`DBMaxOpenConns`は既定値20)に対して負荷をかけた。

### 4.1 ベースライン

| エンドポイント | 同時接続数 | 結果 |
| --- | --- | --- |
| `GET /health/live`(DBに触れない) | 50 | 1,000,000リクエスト、失敗0、p99 1.5ms |
| `GET /health/ready`(DB 1クエリ) | 50 | 453,903リクエスト、失敗0、p99 4.7ms |

いずれも良好。`DBMaxOpenConns=20`を上回る同時接続数(50)でも、超過分は単に接続プールで待たされるだけでエラーにはならないことを確認した。

### 4.2 発見したボトルネック: `GET /api/missions`のコネクションプール枯渇

同じ条件(同時接続50)で認証済み`GET /api/missions`(ミッションテンプレート一覧)を試したところ、劇的に異なる結果になった。

| 同時接続数 | 結果(修正前) |
| --- | --- |
| 10〜30 | 良好(3,500〜7,700 req/s、失敗0) |
| 35 | 悪化開始(1,959 req/s、504が出始める) |
| 40〜50 | **崩壊(105〜109 req/s、大半が504タイムアウト)** |

**原因調査**: `backend/internal/repository/template_repo.go`の`ListByUser`が、外側のクエリ(`mission_templates`一覧)の`*sql.Rows`カーソルを開いたまま、ループの各反復で内側のクエリ(`scheduleDaysFor`、スケジュール曜日の取得)を実行していた。この実装では、1件のリクエストが「外側クエリ用に1コネクション保持したまま、内側クエリ用にもう1コネクションを要求する」ため、同時接続数が接続プールの上限(`DBMaxOpenConns`)に近づくと、**すべてのリクエストが外側の1本を握ったまま内側の1本を待ち続け、誰も先に進めなくなる**という接続プールの共食い(セルフスタベーション)が発生していた。10〜30接続では偶然プール内で捌ききれていたが、35を超えたあたりから雪だるま式に悪化し、40以上でほぼ完全に詰まっていた。

**修正**: 外側のクエリの`rows`を(ループが終わったら即座に)明示的に閉じてから、集めたテンプレートID全件分のスケジュール曜日を**1回のクエリ**(`WHERE mission_template_id = ANY($1)`、pgxドライバはGoの`[]string`をPostgresの配列パラメータとしてネイティブに扱えるため追加のライブラリ不要)でまとめて取得し、テンプレートIDごとにグルーピングして割り当てる方式に変更した。これにより、テンプレート件数によらず常に2クエリで完結し、クエリの重なりによる接続保持の問題自体を解消した。

**修正後の再検証**(同じ同時接続数):

| 同時接続数 | 結果(修正後) |
| --- | --- |
| 40 | 70,958リクエスト、失敗0、p99 8.4ms |
| 50 | 67,011リクエスト、失敗0、p99 12.4ms |
| 80(未検証だった範囲まで拡張) | 63,636リクエスト、失敗0、p99 23.8ms |

崩壊が完全に解消され、むしろ修正前の「良好」だった範囲(10〜30接続)より大幅に高いスループットを達成した(1+Nクエリが常に2クエリになったことによる副次効果)。

**正確性の確認**: 異なるスケジュール曜日を持つ複数のテンプレートを作成し、`GET /api/missions`が各テンプレートに正しく自分の曜日だけを返す(他のテンプレートの曜日と混ざらない)ことを確認した。

**回帰テストの追加**: `backend/internal/handler/router_integration_test.go`に2件追加した。

- `TestListMissions_EachTemplateGetsItsOwnScheduleDays`: グルーピングロジックの正しさを検証(バグ修正前のコードでもこのテスト自体は通ってしまう — バグはデータの誤りではなく負荷時の詰まりのため、別テストが必要)。
- `TestListMissions_Concurrent`: 同時接続数100で`GET /api/missions`を一斉に叩き、全件200になることを検証。**この同時接続数(100)は経験的に決めた** — 25では(1回きりのバーストでは)修正前のコードでも再現しなかったが、100では確実に504が再現することを確認した上で採用した。実際に修正前のコードへ一時的に戻し、このテストが失敗すること(そして修正を戻すと1秒程度で成功すること)を確認済み(フェーズ13の`TestMigrate_ConcurrentInstancesDoNotRace`と同じ検証の徹底度)。

### 4.3 他の認証済みエンドポイントのスポットチェック

同様の問題が他に潜んでいないか、`GET /api/missions/today`・`GET /api/stats`・`GET /api/missions/history`を同時接続50で確認した。**いずれも問題なし**(4,900〜7,800 req/s、失敗0)。`backend/internal/repository`内の他のクエリ関数を確認したところ、カーソルを開いたまま内側クエリを発行しているのは`TemplateRepo.ListByUser`のみだった(`DailyMissionRepo`の一覧系メソッドはループ内で追加クエリを発行しない設計になっている)。

### 4.4 ログインエンドポイントの固有コスト(bcrypt)

ログインエンドポイント自体は、フェーズ16で追加したレート制限(クライアントIPごとに5回/6秒)により意図的にスループットが絞られているため、本フェーズの負荷試験の対象からは除外した。参考情報として、`bcrypt.DefaultCost`(10)でのハッシュ比較コストを単体で計測したところ、1回あたり平均45.4ms(コア1つあたり理論上限約22 req/s)だった。これはbcryptが意図的に低速であることによる設計通りのコストであり、バグではない。実際のログイン試行がこの上限に達する前に、フェーズ16のレート制限(1クライアントあたり0.83 req/s)がはるかに低い値で先に効くため、実運用上のボトルネックにはならないと判断した。

## 6. 検証結果まとめ

- バックエンド回帰確認: `gofmt -l .`(差分なし)・`go build ./...`・`go vet ./...`・`go test ./... -race`・統合テスト(実DB、`-race`、新規2件を含む全9件)すべて成功。
- 片系停止試験: 実際のNginx+2インスタンス構成で、片系を`docker kill`しながら20万件超のリクエストを流し、失敗0件を確認。
- DB障害試験: 実際にDBコンテナを停止・再起動し、`/health/ready`の状態遷移・自動再接続・ログの健全性(panic/fatalなし)を確認。
- ロールバック演習: 実際の`deploy.sh`ロジックで、v1→v2(意図的な退行)→v1(ロールバック)の一連の流れを実行し、最終的に正常な状態へ復帰することを確認。
- 負荷試験: `hey`による実測で、修正前は同時接続40〜50で崩壊(105 req/s)していたエンドポイントが、修正後は同条件で健全(70,000+ req/s)になることを確認。他の認証済みエンドポイントに同様の問題がないことをスポットチェックで確認。
- すべてのテスト・ローカル検証用のDockerコンテナ・イメージ・スクラッチファイルは検証後に削除済み。

## 7. セキュリティ上の確認

本フェーズで発見・修正したバグはパフォーマンス上の問題であり、認可・認証・秘密情報の扱いには影響しない(`ListByUser`は引き続き`user_id`で絞り込んだクエリのみを発行する)。ロールバック演習で使った「意図的な退行を仕込んだコード」は、この演習専用にスクラッチ領域でのみビルドし、実リポジトリには一切コミットしていない。さくらのクラウードの有料リソース作成、`terraform apply`、Git commit・push、破壊的操作は一切実施していない(ローカルDocker環境に対する`docker kill`/`docker stop`は、本フェーズの障害試験として意図的に実行したものであり、対象は本フェーズ専用に起動した使い捨てのコンテナ)。

## 8. 残っている課題

- **さくらのクラウードの実LB・実DBアプライアンス・実CDパイプラインでの試験**は、アプリサーバ・DBアプライアンスが実際に`terraform apply`されるまで実施できない(1〜3節で明記した実機との違いを参照)。
- **ヘルスチェックだけでは検知できない種類の退行がある**(3節)。デプロイ後の自動スモークテスト(ログイン等の主要フローを実際に叩く)をCD(フェーズ13)に追加するかどうかは、フェーズ18の運用手順書で検討する。
- レート制限がプロセスローカルであること(フェーズ16から継続)の、production環境2台構成での実効的な挙動の実地確認。
- Grafana Cloud側のアラート(フェーズ14で設計のみ)が、本フェーズで見つかったような性能崩壊を実際に検知できるかは未検証(Grafana Cloudアカウント未作成のため)。
- 片系停止試験・DBフェイルオーバー演習の実施記録は、実インフラ構築後にフェーズ17を改めて実施し、本ドキュメントを更新することが望ましい。
