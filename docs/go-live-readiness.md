# 公開判定(Go-Live Readiness)

最終更新: 2026-09-23(フェーズ18)

## 判定結果: 条件付きGO

**コード・インフラ設計は本番公開の準備が整っている。** 一方で、実際の公開には、このセッション(Claude Code)の権限外にある一連の手動作業 — さくらのクラウードの実リソース作成・DNS変更・実在の秘密情報の発行 — が必須であり、これらはこのプロジェクトを通じて一貫して「ユーザー自身が行う操作」として明確に線引きしてきた(`docs/production-roadmap.md`の全フェーズで、`terraform apply`・DNS変更・Git push・破壊的操作を一度も実施していないことを繰り返し記録している通り)。

したがって判定は「無条件GO(=今すぐ公開できる)」でも「NO-GO(=コードに問題があり公開すべきでない)」でもなく、**「公開判定チェックリスト(2節)を満たせば公開してよい」という条件付きGO**である。

## 1. 完了していること(検証済み)

18フェーズすべてを完了し、それぞれ実際のツール・実際のローカル環境での検証を伴っている(推測・机上の設計のみで終わらせたフェーズはない)。主な検証の実例:

- バックエンド/フロントエンドの自動テスト(単体・統合、実DB使用)が整備され、CIに組み込まれている。
- 実際のGrafana Alloyバイナリ・`govulncheck`・`trivy`・`npm audit`・`hey`(負荷生成)・`actionlint`・`shellcheck`など、断定ではなく実際のツールでの検証を積み重ねてきた。
- フェーズ16で実コードから到達可能な**SQLインジェクション脆弱性**(`pgx`ドライバ)を発見し修正、フェーズ17で**コネクションプール枯渇によるスループット崩壊**(105 req/sまで低下)を発見し修正、フェーズ18で**セッションテーブルの無限増殖**(フェーズ2から指摘されたまま放置されていた)を発見し修正——単なるチェックリストの消化ではなく、実際に動くものに対して実際に負荷・攻撃的な条件をかけて問題を見つけ、直す、というサイクルを複数回実施した。
- 障害試験(片系停止・DB断・ロールバック)をローカルシミュレーションで実施し、いずれも設計通りに機能することを確認した。

## 2. 公開前に必須の手動対応チェックリスト

これらを満たさない限り、`terraform apply`自体が実行できない、または実行しても安全に運用できない。詳しい手順は`docs/operations-runbook.md`2節。

- [ ] さくらのクラウードアカウント・APIキーの発行
- [ ] さくらのクラウードの各種プラン名・イメージ名の最新値の確認(`os_type`・DBの`plan`/`database_version`・LBの`plan`など、コード中に「要確認」と明記した暫定値)
- [ ] デプロイ用SSH鍵ペアの生成
- [ ] 管理者IPアドレス(`admin_ssh_cidrs`)の確定
- [ ] `matsu0122.com`ゾーンの管理場所の確認
- [ ] `terraform apply`の実行(staging→production推奨順、production側は2段階ブートストラップに注意)
- [ ] `.env`・TLS証明書・`monitoring.env`の各アプリサーバへの手動投入
- [ ] DNSレコードの設定
- [ ] GitHub Secrets(`DEPLOY_SSH_KEY`等)・Environment保護ルールの設定

**これらはすべて実在の認証情報・実際の費用発生・実際のドメイン制御を伴う操作であり、このセッションでは実施していない(実施できない、ではなく、プロジェクトの一貫した方針として実施しない)。**

## 3. 公開直後〜早期に対応すべき事項

公開そのものを妨げないが、公開後なるべく早く対応すべき。

- Grafana Cloudアカウントの作成とアラートルールの実装(`docs/monitoring-design.md`6節) — これがないと、性能劣化やエラー率上昇を能動的に検知する手段が外形監視(死活のみ)しかない。
- GitHub Environment `production`のRequired reviewers設定 — 未設定のままだと、誰でも(リポジトリへの書き込み権限があれば)productionへ直接デプロイできてしまう。
- TLS証明書の実際の発行・自動更新の実装 — 現状は手動更新が前提の設計。

## 4. 長期的な改善事項(公開を妨げない)

`docs/operations-runbook.md`8節の表を参照。Terraform stateのリモートbackend移行、DB冗長構成(フェイルオーバー)、デプロイ後の自動スモークテストなど。

## 5. この判定の限界

この判定は、これまで18フェーズにわたってこのセッション群が実施してきた検証(コードレベルのテスト・ローカルでのインフラシミュレーション・静的解析・依存関係スキャン)に基づく。**実際のさくらのクラウード上での動作(実LB・実DBアプライアンス・実際のネットワーク遅延・実際のトラフィックパターン)は一度も検証されていない。** 2節のチェックリストを満たして初回`apply`・初回デプロイを行った後、`docs/operations-runbook.md`2.6節の動作確認を必ず実施し、可能であれば`docs/tls-design.md`7節の片系停止試験を実インフラに対しても一度実施することを強く推奨する。
